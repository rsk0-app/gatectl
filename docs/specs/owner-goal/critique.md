## 1. INV-02 запрещает необходимую привязку проверок к дереву репозитория
SEVERITY: high

Ответ автора на замечание № 5 допускает, что gates видят `docs/goal.yaml` как часть дерева. Но пересмотренный INV-02 по-прежнему требует, чтобы содержимое этого файла **никогда не меняло ответы** `next`, completion и `commit-check`. Это несовместимые требования.

Сценарий: проверки пройдены для дерева A → `goal confirm` записывает подтверждение в отслеживаемый `docs/goal.yaml` → пользователь добавляет изменение в индекс → получается дерево B. Существующий `treeDigest` в `src/core/target.mjs` учитывает весь индекс, а проверка завершения в `src/cli/commands.mjs` сравнивает его с сохранённым деревом. Результат должен устареть, поэтому ответ команды меняется — вопреки INV-02. Исключение файла из привязки, напротив, позволит подтверждать дерево, отличающееся от проверенного.

Исправление: запретить использование **смысла цели и статуса подтверждения** как gate evidence, но явно разрешить обычный учёт файла в дереве, изменённых путях и проверках репозитория. Требование неизменности ответов сохранить для внешних журналов.

RESOLVED: INV-02 now forbids interpreting the goal or its status as gate evidence and reading the logs, while stating that docs/goal.yaml is ordinary repository content for tree binding and changed paths; only the external logs must leave answers unchanged (AC-05).

## 2. Двенадцать hex-символов не обеспечивают заявленную связь с точным содержимым
SEVERITY: high

В ответе на замечание № 2 утверждается: «any edit yields a new id needing a new confirmation». Для выбранного усечения SHA-256 это утверждение ложно: идентификатор содержит всего 48 бит.

Сценарий: агент заранее перебирает варианты двух документов — с допустимой целью A и с нежелательной целью B, меняя свободный текст критериев. Поиск совпадения между двумя семействами требует порядка десятков миллионов вычислений хеша, а не взлома полного SHA-256. Найдя одинаковые первые 12 hex-символов, агент предлагает A → владелец отправляет точное подтверждение → агент заменяет согласуемое содержимое на B. Идентификатор остаётся прежним, поэтому `goal confirm` принимает сообщение, а статус не показывает изменение. Проблема сохраняется даже при идеально работающем журнале наблюдений.

Исправление: использовать полный SHA-256 для связи предложения, сообщения владельца и подтверждения. Короткий префикс можно показывать для удобства, но нельзя использовать как единственное проверяемое доказательство совпадения содержимого. Добавить тест с разными полными digest, имеющими одинаковый короткий префикс.

RESOLVED: The id is the full 64-hex sha256; the confirmation message and every comparison use the full id, a prefix is display only. AC-02 checks that a message naming only a prefix does not confirm.

## Answered in earlier rounds

> ## 1. Отказ владельца удовлетворяет правилу подтверждения
> SEVERITY: high
> 
> Сценарий: после черновика hook записывает сообщение «Я не подтверждаю эту цель». Агент запускает `goal confirm --quote "подтверждаю эту цель"`. Подстрока найдена, время подходит, digest совпадает → цель получает статус «подтверждена владельцем», хотя владелец отказал. Даже полная цитата отказа удовлетворяет описанному алгоритму: положительное решение вообще не проверяется.
> 
> Исправление: ввести явный формат подтверждения с идентификатором предложения, который владелец отправляет отдельным сообщением. Проверять полное сообщение после строго определённой нормализации. Произвольное совпадение цитаты может доказывать только наблюдение текста, но не согласие.
> 
> RESOLVED: Confirmation is no longer a quote match. Only a prompt whose whole normalized text is exactly `подтверждаю цель G-<id>` or `confirm goal G-<id>` counts; a refusal containing the words does not. AC-02 tests a refusal.

> ## 2. Согласие с одной версией подтверждает другую
> SEVERITY: high
> 
> Сценарий: агент создаёт цель A → владелец читает A и подтверждает её → агент вручную заменяет содержимое на B → вызывает `goal confirm` с настоящей цитатой владельца. Команда записывает digest текущей B. Сообщение поступило после черновика, digest совпадает → B считается подтверждённой, хотя владелец её не видел.
> 
> Правило «changed since confirmation» не помогает: подмена произошла **до** выполнения команды подтверждения.
> 
> Исправление: связывать предложение с неизменяемым идентификатором и digest при создании черновика. Подтверждающее сообщение должно указывать это предложение. Любое изменение согласуемого содержимого должно создавать новую версию, требующую нового подтверждения.
> 
> RESOLVED: The draft id is a digest of all agreed content, fixed at propose time; the confirmation message names that id; confirm records only the current id, and any edit yields a new id needing a new confirmation. AC-02 tests confirming an earlier id.

> ## 3. Ограничение журнала конфликтует с сохранением подтверждения
> SEVERITY: high
> 
> Сценарий: цель подтверждена через наблюдавшееся сообщение → приходят ещё 200 сообщений → исходная запись удаляется. INV-01 требует наличия цитаты в hook-observed prompt, но подтверждение хранит только цитату, время и digest содержимого цели.
> 
> Получаются два несовместимых поведения: повторная проверка журнала отменяет ранее полученное подтверждение; доверие полям `docs/goal.yaml` позволяет агенту самостоятельно записать те же поля, возвращая исходную проблему «агент написал, что владелец согласился». Аналогичная ситуация возникает при клонировании репозитория без локального журнала.
> 
> Исправление: определить отдельную сохраняемую запись наблюдения, связанную с версией предложения, и правила её проверки. Различать статусы «подтверждение наблюдалось локально» и «подтверждение записано в репозитории, локально не проверено». Явно описать поведение после очистки журнала и на другом компьютере.
> 
> RESOLVED: Dedicated confirmation messages go to a separate, never-rotated owner-confirmations.jsonl. Status distinguishes confirmed (observed here) from 'confirmed elsewhere (not verified here)' when the repository records a matching id but this machine has no observation. AC-02 tests the missing-log case.

> ## 4. Подтверждённый документ допускает подмену слов владельца
> SEVERITY: medium
> 
> Сценарий: владелец подтверждает документ с цитатой «Нужен небольшой внутренний инструмент» → агент меняет `owner words` на «Нужна публичная платформа», а также автора и дату подготовки. Goal, success criteria и out-of-scope остаются прежними → digest совпадает, общий статус остаётся подтверждённым.
> 
> Это позволяет предъявить изменённые слова как часть согласованного требования. Формулировка «Any later change to those» защищает только три перечисленных поля, хотя документ содержит и другие значимые утверждения.
> 
> Исправление: либо включить все согласуемые поля в digest, либо показывать подтверждение отдельно для конкретных полей. Наблюдаемость каждой цитаты должна проверяться по её текущему содержимому, а не по сохранённому флагу.
> 
> RESOLVED: The id covers all agreed fields including owner words; editing any of them reports changed since confirmation. Quote observation is computed from the log at propose/show time, not trusted from a stored flag. AC-02 edits owner words.

> ## 5. AC-05 допускает запрещённое влияние контекста на gates
> SEVERITY: high
> 
> Сценарий: `next` импортирует общий модуль из `src/context/**`, а тот читает `docs/goal.yaml` или журнал и возвращает статус подтверждения. `next` использует этот статус для решения → прямого импорта goal-модуля нет, AC-05 проходит, но INV-02 нарушен. Использование журнала контекста как доказательства также прямо противоречит declared OUT OF SCOPE.
> 
> Аналогично, прямое чтение файла через `fs` вообще не требует импорта goal-модуля.
> 
> Исправление: проверять транзитивные зависимости и фактические обращения к файлам. Добавить проверки, что изменение, удаление и повреждение goal-файла и журнала не меняет решения и exit codes у gate, `next`, `commit-check` и `finish`. Проверка отсутствия одного импорта недостаточна.
> 
> RESOLVED: AC-05 checks the transitive import graph from gate/next/completion/attestation modules (neither the goal module nor the context layer) and that next --json and status answer identically with both logs absent, populated and corrupted. docs/goal.yaml is a repository file like any other; gates see it only as part of the tree.

> ## 6. Параллельные hooks могут потерять единственное подтверждение
> SEVERITY: medium
> 
> Сценарий: два сеанса одновременно читают журнал из 199 записей. Первый добавляет подтверждение владельца, второй — другое сообщение. Оба сохраняют собственную версию последних 200 записей → последняя запись файла стирает результат первого hook. Подтверждение действительно наблюдалось, но `goal confirm` возвращает `OWNER_CONFIRMATION_NOT_OBSERVED`.
> 
> Если вместо перезаписи использовать только append, параллельные записи и очистка требуют отдельного протокола, иначе ограничение в 200 записей также не гарантируется.
> 
> Исправление: определить атомарный протокол добавления и очистки с координацией между процессами, ограниченным ожиданием и явным поведением при сбое. Проверить одновременную запись нескольких hooks и сохранность подтверждающего сообщения. Однопроцессный AC-04 этот сценарий не покрывает.
> 
> RESOLVED: Appends use O_APPEND; rotation of the prompt log runs under a lock with bounded wait and is skipped when busy; confirmations live in a never-rotated file. AC-04 runs concurrent hooks and checks every confirmation message survives.

> ## 7. Обрезка сообщения уничтожает требуемые дословные слова
> SEVERITY: medium
> 
> Сценарий: владелец присылает описание длиной 4500 символов, а ключевая формулировка находится после позиции 4000. Hook сохраняет только начало. Агент передаёт ключевую фразу в `--owner-words` → она отмечается ненаблюдавшейся, хотя hook получил её. Подтверждение в конце длинного сообщения тоже будет отвергнуто.
> 
> AC-01 обещает наблюдаемость тогда, когда prompt содержит цитату, а правило хранения позволяет удалить эту цитату. Различие между полученным и сохранённым сообщением нигде не определено.
> 
> Исправление: явно ограничить проверку сохранённой частью сообщения, хранить признак обрезки и возвращать отдельную причину «текст вне сохранённого фрагмента». Для подтверждения предусмотреть короткое самостоятельное сообщение и соответствующий тест.
> 
> RESOLVED: Stored prompts carry a truncated flag; propose reports a quote as not verifiable when truncated prompts exist rather than as absent; confirmation is a short dedicated message, never affected by truncation. AC-04 checks the cap and flag.
