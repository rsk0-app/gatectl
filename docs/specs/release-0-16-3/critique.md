## 1. `finish` CLI unnamed; 0.16.0 host cache would sign a completion the released hook cannot recognize

SEVERITY: high

Session prompt says bundled CLI is `~/.claude/plugins/cache/gatectl/gatectl/0.16.0/bin/gatectl.mjs`. Spec never says which binary runs `task start`/`finish`. Runtime at 6da2cf1 adds `input_context` to completion on successful finish (`docs/specs/stop-completion-context/spec.md:12`, README:1063 "Pre-0.16.3 completions lack this binding"). 0.16.0 has no such code.

Scenario: implementer enrolls and finishes via the 0.16.0 cache CLI → exit 0, completion.json without `input_context`. Commit, push, tag, install 0.16.3. First new thread in this repo: Stop runs `next --recorded-completion`, finds legacy record, falls back to normal next → "checks stale" reminder on the release commit itself. The fix being shipped fails on its own release. Refresh then requires a second `finish` under the original env, which spec.md forbids conflating with hand edits but never schedules.

Fix: spec.md states "task enrollment and finish run `node bin/gatectl.mjs` from this checkout at 6da2cf1, not any host plugin cache". Add post-finish step: confirm completion.json carries `input_context` before tagging.

RESOLVED: Spec names checkout node bin/gatectl.mjs for enrollment and finish and requires input_context/attestation/MAC linkage verification before tagging. This checkout contains accepted fix 6da2cf1.

Current thread stays on 0.16.0 and is expected to hit the old bug after commit; say so.

RESOLVED: Corrected host evidence: Codex installed 0.16.2 from the verified local marketplace; current path is an existing development compatibility directory, not the critic’s Claude 0.16.0 release cache. No bare-version cache binaries will be overwritten. Back up the development alias outside cache, replace it with an explicit symlink to the installed 0.16.3, verify realpath/version/hook and document rollback retargeting.
